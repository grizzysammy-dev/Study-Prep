# iptables

iptables is the Linux kernel firewall. It inspects packets at fixed points and decides ACCEPT, DROP, or rewrite. The picture that keeps it straight in my head: every packet walks down a corridor with an inspection desk at each doorway (just arrived, about to be routed, meant for us, on its way out), and at each desk a guard reads top-to-bottom down a checklist, does whatever the first matching line says, and stops. That's the whole machine, checklists (rules) bolted to doorways (chains), running inside the kernel before my services ever see the traffic.

This is one of the heavily tested JQR projects in Module 1, so I want the build order to be automatic: a safe default-deny host firewall, NAT between subnets, and rules that survive a reboot on both Debian/Ubuntu and CentOS.

## The set I keep coming back to
```bash
# safe host firewall — allow FIRST, DROP policy LAST (never lock yourself out)
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT        # SSH — add BEFORE the drop
sudo iptables -P INPUT DROP                               # flip the policy LAST
sudo iptables -L -n -v --line-numbers                     # read the ruleset (with counters)
sudo iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o ens33 -j MASQUERADE   # SNAT out
sudo iptables-save > /etc/iptables/rules.v4              # persist Debian/Ubuntu
sudo service iptables save                               # persist CentOS (/etc/sysconfig/iptables)
```

## How it works
### Tables (what kind of processing)
| Table | Used for |
|---|---|
| `filter` | the default: allow/deny (INPUT, OUTPUT, FORWARD) |
| `nat` | rewrite address/port (PREROUTING, POSTROUTING, OUTPUT), masquerade, port-forward |
| `mangle` | alter fields (TTL, TOS, marking), advanced stuff |
| `raw` | conntrack exemptions, rarely need it |

### Chains (where in the packet's journey rules run)
| Chain | Fires on... |
|---|---|
| `INPUT` | packets **destined for this host** |
| `OUTPUT` | packets **generated by this host** |
| `FORWARD` | packets **passing through** (routed), needs `ip_forward=1`, see [Interfaces IPs and Routing](../Linux%20Admin/Interfaces%20IPs%20and%20Routing.md) |
| `PREROUTING` | as packets **arrive**, before the routing decision (DNAT) |
| `POSTROUTING` | just **before packets leave**, after routing (SNAT/MASQUERADE) |

### The four ideas that actually matter
- **Order:** top-to-bottom, **first match wins**. The first matching rule decides the packet and processing stops, so specific ACCEPTs go **above** broad DROPs.
- **Policy (`-P`):** what happens to a packet that matches **no** rule in a built-in chain. Whitelist (secure) is policy DROP plus explicit ACCEPTs; blacklist (loose) is policy ACCEPT plus specific DROPs.
- **Stateful filtering (conntrack):** `NEW` / `ESTABLISHED` / `RELATED` / `INVALID`. One rule that allows `ESTABLISHED,RELATED` lets replies back in without me writing a matching OUTPUT rule for every service. This is the single most important idea for a clean ruleset.
- **DROP vs REJECT:** DROP is silent (attacker just sees a timeout); REJECT politely replies "closed" and reveals a host is there. I default to **DROP** for stealth on a hardened host.

### Command grammar
```text
iptables -A <CHAIN> [match conditions] -j <TARGET>
  -A append  -I insert(top)  -D delete  -L list  -S dump-rules  -F flush  -P policy
  -p tcp|udp|icmp   --dport N   -s SRC   -d DST   -i IN_IF   -o OUT_IF
  -m conntrack --ctstate NEW,ESTABLISHED,RELATED,INVALID
  -j ACCEPT|DROP|REJECT|LOG|SNAT|DNAT|MASQUERADE|REDIRECT
  -t nat|mangle          # default table is filter
```

## Building a host firewall in the right order
> [!danger] The one mistake I never want to make: running `-P INPUT DROP` **before** the SSH allow rule. On a remote box that instantly kills the session and locks me out. Allow **loopback + established + SSH FIRST**, then flip the policy to DROP **LAST**.

(Still need to actually run this on a VM I can console into. Live firewall rules need root and I don't want to strand myself over SSH.)

```bash
sudo iptables -F                                                   # 1. start clean
sudo iptables -A INPUT -i lo -j ACCEPT                             # 2. loopback must always work
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT   # 3. keep return traffic (incl. your SSH)
sudo iptables -A INPUT -m conntrack --ctstate INVALID -j DROP      # 4. bin obviously broken packets
sudo iptables -A INPUT -p tcp --dport 22  -j ACCEPT               # 5. SSH  (BEFORE the drop policy!)
sudo iptables -A INPUT -p tcp --dport 80  -j ACCEPT               #    HTTP
sudo iptables -A INPUT -p tcp --dport 443 -j ACCEPT               #    HTTPS
sudo iptables -A INPUT -p icmp --icmp-type echo-request -j ACCEPT #    ping
sudo iptables -A INPUT -j LOG --log-prefix "iptables-DROP: " --log-level 4   # 6. log the leftovers
sudo iptables -P INPUT DROP                                        # 7. ONLY NOW deny everything else
sudo iptables -P FORWARD DROP                                      #    not a router? deny transit
sudo iptables -P OUTPUT ACCEPT                                     #    usually let our box talk out
```
Cheap safety net before flipping to DROP on a box I could lose: `sudo sh -c 'sleep 300 && iptables -F' &` auto-flushes in 5 minutes if I strand myself.

I built the same allow-SSH/HTTP/HTTPS/ICMP + established, then log-and-drop logic into a custom chain called `LABDEMO` and dumped it with `iptables -S`. Output when I ran it (Ubuntu 24.04):
```
$ iptables -S LABDEMO
-N LABDEMO
-A LABDEMO -i lo -j ACCEPT
-A LABDEMO -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
-A LABDEMO -p tcp -m tcp --dport 22 -j ACCEPT
-A LABDEMO -p tcp -m tcp --dport 80 -j ACCEPT
-A LABDEMO -p tcp -m tcp --dport 443 -j ACCEPT
-A LABDEMO -p icmp -j ACCEPT
-A LABDEMO -j LOG --log-prefix "DROP-LAB: "
-A LABDEMO -j DROP
```
`-S` prints the rules as the `iptables -A ...` commands that would recreate them, which is the fastest way to screenshot and verify a build. The order is exactly the sequence above: loopback, established, service ports, LOG, DROP.

### Block everything except SSH
The classic JQR one-liner set, order kept so I never lose the session.
```bash
sudo iptables -F
sudo iptables -A INPUT -i lo -j ACCEPT                                        # loopback
sudo iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT   # return traffic
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT                            # SSH in
sudo iptables -P INPUT DROP                                                   # everything else denied
sudo iptables -P FORWARD DROP
sudo iptables -P OUTPUT ACCEPT
```
Only inbound SSH (plus replies to connections we started) survives; everything else inbound is dropped silently. Check it with `sudo iptables -L -n -v --line-numbers`.

## NAT: MASQUERADE and SNAT (rewrite the source, on the way OUT)
Scenario is the box acting as a router/pivot. Hosts on `10.10.10.0/24` (behind `ens34`) need to reach the primary LAN/internet through `ens33`. Their private source has to be rewritten to the box's `ens33` address or replies have nowhere to come back to. Source NAT lives in **POSTROUTING**, the last stop before the packet leaves. You need `net.ipv4.ip_forward=1` (see [Interfaces IPs and Routing](../Linux%20Admin/Interfaces%20IPs%20and%20Routing.md)) and a FORWARD allow first.

The way it actually works: the box records every rewrite in its conntrack table, so when a reply lands on its address it knows which private host to hand it back to, and rewrites the destination back before forwarding it inward. NAT is really "lie about the address on the way out, un-lie on the way back," and conntrack is the memory that makes the un-lying possible. DNAT (below) is the same trick aimed the other way, rewriting the destination on the way in. This is also why NAT is a pain on the blue side, since the collector sees the router's address instead of the real internal host unless you log the translation.

**MASQUERADE** is for when the outgoing IP is dynamic (DHCP); it auto-detects the interface's current address.
```bash
sudo iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o ens33 -j MASQUERADE
sudo iptables -A FORWARD -i ens34 -o ens33 -j ACCEPT
sudo iptables -A FORWARD -i ens33 -o ens34 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
```
**SNAT** is for when the outgoing IP is static and known (slightly faster, no per-packet lookup).
```bash
sudo iptables -t nat -A POSTROUTING -s 10.10.10.0/24 -o ens33 -j SNAT --to-source 192.168.1.50
```
| | **MASQUERADE** | **SNAT** |
|---|---|---|
| Source IP | auto = interface's current IP | you specify it (`--to-source`) |
| Best for | dynamic/DHCP/VPN uplinks | static uplink IP |
| Cost | recomputes per packet | fixed, marginally faster |

## DNAT / REDIRECT (rewrite the destination, on the way IN)
Scenario: anything hitting the router's `ens33` address on TCP 8080 should be forwarded to internal host `10.10.10.20:80`. Destination NAT lives in **PREROUTING**, before the routing decision.
```bash
sudo iptables -t nat -A PREROUTING -i ens33 -p tcp --dport 8080 -j DNAT --to-destination 10.10.10.20:80
sudo iptables -A FORWARD -p tcp -d 10.10.10.20 --dport 80 -j ACCEPT   # permit the now-forwarded packet
```
Local **REDIRECT** bounces a port on *this* host (e.g. 80 to 8080 for a non-root service):
```bash
sudo iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080
```
> [!warning] NAT gotchas
> - **NAT without forwarding does nothing.** `ip_forward=1` is mandatory for SNAT/DNAT/MASQUERADE between interfaces.
> - **SNAT/MASQUERADE = POSTROUTING (out); DNAT/REDIRECT = PREROUTING (in).** Mixing these up is the most common NAT bug I hit.
> - Keep the **return-path FORWARD rule** (the `ESTABLISHED,RELATED` one) or replies get dropped and you see one-way traffic. Confirm with [Tcpdump](../Recon%20Tools/Tcpdump.md).

## Logging what gets dropped (before the drop)
`LOG` is **non-terminating**, meaning the packet keeps walking the chain, so I put it **immediately before** the drop/policy to record exactly what's about to be denied.
```bash
sudo iptables -A INPUT -m limit --limit 5/min -j LOG --log-prefix "iptables-DROP: " --log-level 4
sudo iptables -A INPUT -j DROP
```
`--log-prefix` tags each line so I can `grep` it out of the noise (keep it short, ~29-char limit); `--log-level 4` is warning; `-m limit` stops a flood filling the disk.

The logs land in the kernel ring buffer:
```bash
sudo dmesg | grep "iptables-DROP"
sudo journalctl -k | grep "iptables-DROP"      # systemd journal (kernel) — see [Logs and journalctl](../Linux%20Admin/Logs%20and%20journalctl.md)
# Debian/Ubuntu also: /var/log/kern.log   |   CentOS: /var/log/messages
```

## Making rules survive a reboot
Live `iptables` rules are RAM-only and vanish on reboot, so I always finish with a save step.

### Debian / Ubuntu (iptables-persistent)
```bash
sudo apt update && sudo apt install iptables-persistent   # prompts to save current v4/v6 rules
sudo iptables-save  | sudo tee /etc/iptables/rules.v4     # save v4 manually
sudo ip6tables-save | sudo tee /etc/iptables/rules.v6     # save v6
sudo netfilter-persistent save                            # snapshot live rules -> those files
sudo netfilter-persistent reload                          # reload from files now
```
At boot, `netfilter-persistent` runs `iptables-restore < /etc/iptables/rules.v4` automatically. The Debian/Ubuntu file is `/etc/iptables/rules.v4`.

### CentOS Stream 10 (the iptables service)
CentOS ships firewalld (nftables backend) by default. For a raw-iptables project I install the iptables service and stop firewalld so they don't fight.
```bash
sudo dnf install -y iptables-nft-services      # older RHEL/CentOS: iptables-services
sudo systemctl disable --now firewalld         # stop firewalld clobbering your rules
sudo systemctl enable --now iptables ip6tables # load rules at boot
sudo service iptables save                      # writes /etc/sysconfig/iptables
# equivalent: sudo sh -c 'iptables-save > /etc/sysconfig/iptables'
```
The CentOS file is `/etc/sysconfig/iptables` (and `/etc/sysconfig/ip6tables`). If a project *allows* firewalld, "allow SSH" is `sudo firewall-cmd --permanent --add-service=ssh && sudo firewall-cmd --reload`, but the JQR asks for iptables, so I mask firewalld and use the raw rules.

> [!warning] Persistence gotchas
> - Don't cross the files up: **Debian/Ubuntu `/etc/iptables/rules.v4`** vs **CentOS `/etc/sysconfig/iptables`**.
> - Rules I `-A` but never **save** are gone after reboot. Always finish with a save.

## nftables, the 2026 reality
- **nftables (`nft`)** is the modern kernel firewall backend; classic `iptables` is now usually the **`iptables-nft` shim**, so you type iptables syntax and it programs nftables underneath. `iptables --version` shows `(nf_tables)`.
- An equivalent exists (`nft add rule inet filter input tcp dport 22 accept`), and firewalld/`nft` are the "native" tools, but the JQR asks for iptables, so I keep iptables syntax as my primary answer and just *know* the shim is there.
- Check/switch backend: `sudo iptables -V`; `sudo update-alternatives --config iptables` (legacy vs nft, rarely needed).

## What I keep forgetting
- **Order = first match wins.** Specific ACCEPTs above broad DROPs, always.
- **DROP-policy lockout:** loopback + established + SSH FIRST, `-P INPUT DROP` LAST; keep a `sleep && iptables -F` safety net.
- **`ESTABLISHED,RELATED` once** saves me from writing an OUTPUT rule per service.
- **NAT needs forwarding.** No `net.ipv4.ip_forward=1` and SNAT/DNAT/MASQUERADE silently do nothing.
- **SNAT/MASQUERADE = POSTROUTING; DNAT/REDIRECT = PREROUTING.**
- **LOG before DROP** (LOG is non-terminating); rate-limit it with `-m limit`.
- **Persistence files differ** (Debian vs CentOS) and live rules die unless saved.
- **`-S` vs `-L`:** `-S` dumps re-runnable rule commands (great for proof); `-L -n -v --line-numbers` is the human-readable audit with packet/byte counters.
- **DROP vs REJECT:** DROP for stealth on a hardened host.
